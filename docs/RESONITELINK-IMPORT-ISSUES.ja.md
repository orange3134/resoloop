# 既存コンテンツを変更せずに管理するためのResoniteLinkへの要望

この文書はIssueの草案です。上流にはまだ投稿していません。根拠は、2026-10-15に実機で確認したResonite `2026.9.18.82`、ResoniteLink `0.13.1.0`、クライアントパッケージ `YellowDogMan.ResoniteLink` `0.13.1`です。パッケージのNuGetリポジトリメタデータが示すコミットは `067afad3d1977b3806cbad077f4e8a534f56f451` です。公開ソース・モデルのドキュメントと実機のReflectionを使用しており、非公開のエンジン実装は転載していません。

2026-10-16に、現在のResoLoop実装、固定バージョンの公開APIモデル・ドキュメント、2026-10-15の検証記録を照合しました。上流の最新リリースを確認したものではありません。[英語版](RESONITELINK-IMPORT-ISSUES.md)。

P0/P1では、4,532個のSlotと8,054個のComponentをワールドへの書き込みゼロで取り込み、取り込み直後のdiffが変更ゼロになることを確認済みです。外部参照・入れ子メンバー参照の管理、分割ファイル間の参照解決、Slot属性の明示的な編集はResoLoop側で実装済みです。19ファイルに分割した取り込みでも、1,949件の参照と7個のSlot属性を明示的に維持する指定を行い、diffが変更ゼロになっています。以下は安全な編集や将来の永続化・再構築に関する制約であり、この読み取り専用の取り込みを妨げるものではありません。提案する最小再現手順に、非公開ワールドのスナップショットは不要です。[参照管理の検証](EXISTING-REFERENCES.md)と[分割ファイル・Slot属性の検証](EXISTING-BUNDLES-SLOTS.md)も参照してください。

## 1. 要素の永続的な識別と、接続先ワールドの実行単位の直接識別

**Issueタイトル案：** 読み取り専用ツール向けに、ワールドの実行単位と要素の永続IDを公開してほしい

**問題：** 同じ親に同名のSlotが複数あっても、タグ追加や名前変更をせずに観測することはできます。しかし、保存・再読み込みでプロトコル上のIDが変わると、元のオブジェクトを確実に再識別できません。今回のワールドには同名の兄弟Slotのグループが480組あり、構造でも区別できないものがあります。インデックスや可変の値による照合は安全ではありません。接続の `uniqueSessionId` はワールドの識別子ではなく、ドキュメントにもワールドや再起動をまたいだ一意性の保証はありません。

**現在の回避策：** 接続先エンドポイントと一致する公式のアナウンスからワールドセッションIDを取得し、インスタンスID、親子関係、Component型を改めて確認します。セッションの変更、対応先の欠落・曖昧さがあれば処理を拒否します。このため、WebSocketの接続先が既知でもUDPディスカバリーが必要です。

**APIへの要望：** 接続中のWebSocketから、ワールド／セッションの実行単位を識別するIDを直接取得できるようにし、再起動・読み込み時の意味を明記してください。ワールドにコンテンツを追加せずに、保存・再読み込みをまたいで維持される不変の識別子をSlot、Component、メンバーに提供してください。複製、ワールドのクローン、アイテムのコピー、削除後の再作成、所有先の変更における動作も定義してください。コピー同士を混同しないよう、永続IDには明示的なワールド／アセットの識別範囲が必要です。

**受け入れ条件：** 区別不能な同名の兄弟Slotを2個取り込み、保存・再読み込み後もそれぞれ一意に再識別できること。片方を複製、または削除後に再作成した場合には別の識別子になること。接続IDやポートが再利用されても、別のワールドまたは別の実行単位への接続を確実に拒否できること。

**根拠：** [IDの有効期間に関するドキュメント](https://github.com/Yellow-Dog-Man/ResoniteLink/blob/067afad3d1977b3806cbad077f4e8a534f56f451/README.md#how-ids-work)、[接続セッションのレスポンス](https://github.com/Yellow-Dog-Man/ResoniteLink/blob/067afad3d1977b3806cbad077f4e8a534f56f451/ResoniteLink/Models/Responses/SessionData.cs)、[アナウンスのモデル](https://github.com/Yellow-Dog-Man/ResoniteLink/blob/067afad3d1977b3806cbad077f4e8a534f56f451/ResoniteLink/Models/ResoniteLinkSession.cs)。

## 2. 既存の旧式インスタンスに対するReflectionと、構造化された失敗理由

**Issueタイトル案：** 既存の旧式ComponentをインスタンスからReflectionし、未対応メンバーと型の欠落を区別できるようにしてほしい

**観測結果：** 既存のインスタンスとそのメンバーは読み取れますが、以下の6型ではReflectionが失敗します。

| 実行時の型（すべて `[FrooxEngine]FrooxEngine` 内） | 観測されたエラー |
| --- | --- |
| `LegacyPanel` | Component type not found |
| `LegacyHorizontalChoiceBar` | Object reference not set to an instance of an object |
| `LegacySlider` | 同じnull参照エラー |
| `LegacyVideoPlayer` | 同じnull参照エラー |
| `PhotonDust.AlphaOverLifetimeLinearGradient` | 同じnull参照エラー |
| `PhotonDust.ColorOverLifetimeLinearGradient` | 同じnull参照エラー |

現在のアダプターはこれらの失敗を `COMPONENT_TYPE_NOT_FOUND` と分類しています。表中の文字列は、返された診断メッセージです。この分類名だけでは、実機のインスタンスが存在しないとは判断できません。インポーターは作成や編集を試みず、観測した状態を保持します。

**再現手順：** 対象の旧式インスタンスを含むワールドで、そのComponentと正確な実行時の型を読み取ります。公式クライアントで、その型のフラット化された定義を要求します。成功するインスタンス読み取りと、失敗する定義取得を比較します。既存インスタンスの調査に、現在の型検索で見つかることや、その旧式の型を新規作成できることを必須にすべきではありません。

**API・修正への要望：** 非推奨の型も含めて、既存のインスタンスIDから定義・対応操作を取得できるようにするか、該当する型ベースのReflectionを修正してください。型の解決失敗、定義の生成失敗、未対応のメンバー、読み取り可能だが新規作成できない型を、構造化された情報で区別してください。不明なメンバーやイベントを誤って書き込み可能と推測しないよう、メンバーごとに読み取り・書き込み・作成の対応状況を示してください。

**受け入れ条件：** これらの既存Componentから、原因が分類されないnull参照エラーではなく、有用な部分定義または完全な定義を取得できること。未対応メンバーには理由が明示され、同じComponent内の対応済みフィールドは管理できること。

**根拠：** [GetComponentDefinitionの契約](https://github.com/Yellow-Dog-Man/ResoniteLink/blob/067afad3d1977b3806cbad077f4e8a534f56f451/ResoniteLink/Models/Messages/Reflection/GetComponentDefinition.cs)。実機での失敗の詳細は、ローカルの `snapshot.json` → `types`、分割取り込みでは `snapshot/dependencies.json` → `types` に保存されています。非公開ワールド全体を、そのままIssueに添付する必要はありません。

## 3. 内容を解釈できないメンバー・イベントの対応操作の明示

**Issueタイトル案：** 内容を解釈できないSyncDelegate・イベントメンバーについて、読み取り可能なメタデータと対応操作を公開してほしい

**観測結果：** グラフの読み取りでは、フラット化されたReflectionに対応する項目がないメンバーや、`empty` メンバーが見つかります。以前の調査では、UIX Buttonのイベント（`Pressed`、`Released`、`HoverEnter`）やTextFieldの編集イベントが例として見つかりました。今回の取り込みには、定義自体は取得できたものの定義内に存在しないトップレベルのメンバーが467個、Reflectionで確認された `empty` メンバーが1,067個含まれます。これらすべてがイベントだと確認されたわけではありません。空のメンバーをすべてデリゲートと見なすのではなく、インスタンスに基づいた対応操作のメタデータで分類する必要があります。

**APIへの要望：** 実際のメンバー種別を示し、そのバインディングや参照先を読み取り・変更できるか明示してください。対応するデリゲート／イベントのバインディングには、型付きの表現と、無関係なバインディングを維持する更新操作を文書化して提供してください。意図的にアクセス不可とする種別には、安定した理由コードや対応可否フラグを提供してください。

**受け入れ条件：** ツールが、空の値、未対応のイベント、Reflection情報を取得できない状態を区別できること。読み書きに対応するバインディングを隔離したComponentで読み取り・変更でき、未対応データは削除せずに保持できること。イベントの発火とバインディングの編集は、別々の対応操作として示されること。

これは不足しているメタデータ・操作への要望であり、定義から省略されたすべてのメンバーを書き込み可能にできる、またはすべきだと主張するものではありません。

## 4. 条件付きフィールド更新と、観測の整合性を確認できるリビジョン

**Issueタイトル案：** フィールドの比較付き更新と、リビジョンを確認できる部分ツリー読み取りを追加してほしい

**問題：** 既存ワールドはimport・diff・applyの間も動き続けます。クライアント側でbaseline・現在値・希望値を比較すれば、書き込み前の変更は検出できますが、最後の読み取りと書き込みの間に別の更新が入る可能性は残ります。また、複数のリクエストによる階層スナップショットは原子的ではありません。構造の再読み取りで構造変更は検出できても、取得したすべての値が同じワールドリビジョンに属することは証明できません。

**APIへの要望：** 期待するメンバーのリビジョン、または型付きの期待値を条件とする更新を提供し、不一致なら書き込みを行わず競合を返してください。ワールドの実行単位の識別子も含めてください。範囲を限定した部分ツリーの読み取りには、リビジョン／スナップショットトークンを提供するか、変化するリビジョンをまたいだ読み取りであることを明示してください。バッチ操作では、トランザクション・部分成功の意味と、フィールドごとの結果を文書化してください。

**最小再現手順：** 隔離した数値フィールドをクライアントが読み取り、実行中のドライバーが値を変更した後、クライアントが古いbaselineを使って書き込みます。クライアントだけでの確認では、この競合を排除できません。現在の実装は書き込み前の変更検出と書き込み後の確認を行いますが、原子性は保証していません。

**受け入れ条件：** 同時更新が発生した場合は競合となり、新しい値・リビジョンが維持されること。シーンに同期用Componentを追加せずに、観測側で取得結果の不整合を検出できること。

**P1での根拠：** Componentのフィールド、参照、Slot属性のいずれにも該当します。参照更新では、構造化された参照元メンバーパスまたはメンバーIDと、期待する参照先／リビジョンを指定できる必要があります。現在の参照リスト更新は、対象を含むComponent経由で隣接要素も送信します。そのため、リスト長と要素IDを維持し、直後に読み戻しても、同時更新の競合が起こり得ます。メンバーごとの条件付き更新では、期待値が古ければ、対象要素にも隣接要素にも変更を加えず拒否する必要があります。クライアント側の競合検出とSlotの部分更新は実装済みであり、ここで求めているのはサーバー側の原子性です。

## 5. Componentを置き換えずに行うリスト要素の削除

**Issueタイトル案：** 要素の同一性と参照の安全性を保ち、既存リストの要素をその場で削除できるようにしてほしい

**問題：** 固定バージョンの連携APIには、既存のSyncListをその場で短くする操作が文書化されていません。生成コンテンツのワークフローではComponentを再作成してリストを短くできますが、取り込んだコンテンツでは、表現できていないメンバーや外部からの参照を失う可能性があるため不適切です。P1ではすでに、リスト長、要素ID、Componentの同一性を維持した参照リスト要素の更新を実装しています。取り込んだリストの縮小・再作成は引き続き拒否していますが、既存リスト内の参照変更は上流APIの不足に妨げられていません。

**APIへの要望：** 要素の同一性、明確なインデックスの意味、条件付きリビジョン、削除される要素への参照の扱いを定義した、既存リストの要素削除または縮小操作を文書化して提供してください。Componentの同一性と無関係なすべてのフィールドを維持してください。対象を参照している箇所を確実に検索できるAPIも、破壊的な編集の影響をツールが説明する助けになります。この草案は、あらゆる挿入・値の置き換え・並べ替えに新しいAPIが必要だと示すものではありません。

**受け入れ条件：** 隔離した2要素のリストを1要素に短縮しても、Component ID、無関係な状態、残した要素への参照が変わらないこと。期待するリビジョンが古ければ、変更を行わず失敗すること。

**根拠：** [SyncListのペイロード](https://github.com/Yellow-Dog-Man/ResoniteLink/blob/067afad3d1977b3806cbad077f4e8a534f56f451/ResoniteLink/Models/DataModel/SyncList.cs)。この草案の対象は固定バージョン0.13.1との連携です。実装済み機能への重複要望を避けるため、投稿前に上流の新しい変更を確認してください。

## 6. 汎用の要素IDから参照先の所有先・パス・型を解決するAPI

**Issueタイトル案：** 任意の参照先IDから、読み取り可能な所有関係と型付きメンバーメタデータを取得できるようにしてほしい

**P1での観測：** WorldRootの取得結果には、異なる144個の参照先に向けた1,073件の外部参照があります。Component／Slotを正確なIDで読み取ることで143個を識別できました。残る1個（今回のセッションでは `Reso_14E81`、2本の参照エッジから参照）は、どちらの操作でも解決できません。これは参照先が存在しないことを示しません。メンバー、またはSlot／Componentではない実行時オブジェクトの可能性があります。固定バージョンの公開メッセージモデルにはComponent／Slotの読み取りはありますが、汎用の要素IDから所有先・パス・型を検索する操作はありません。無関係なコンテンツを走査して解決しようとすると、探索範囲を限定できず、それでも実行時オブジェクトを見つけられない可能性があります。

**APIへの要望：** 正確なIDを指定する読み取り専用の検索で、要素種別、実際の型・代入可能な型、該当する場合の所有Component／Slot、構造化されたメンバーパス、有効期間の範囲、対応操作のフラグを返してください。存在しない、読み取り不可、未対応、実行時にのみ存在する参照先を区別してください。クライアントが非公開のSyncラッパーを再構築しなくても、SlotメンバーやSyncObject・リスト・辞書内の参照を扱えるようにしてください。マーカーの追加や、依存先を管理対象として所有することを必要としないAPIを求めています。

**最小再現手順：** 隔離して管理するComponentから、外部Componentのメンバー、Slotメンバー、または実行時のUserオブジェクトを参照させます。参照元から参照先IDを読み取り、ワールド全体を走査せずに、そのIDを直接解決します。Issueの再現に、非公開ワールドのスナップショットや今回のセッション限定の例示IDは不要です。

**受け入れ条件：** 読み取り権限に従いながら、ツールが参照先に名前を付けて型を検査し、所有先・構造化されたパスを検証できること。未対応の参照先と存在しない参照先を区別できること。リストの並べ替え後も、要素の同一性を確認する情報が維持されること。削除済みの参照先には、存在しないことを明示する結果が返ること。

**現在の動作：** P1は解決できないバインディングを名前付きの依存先として保持しますが、その参照先を新たに指定する操作は拒否します。内部の入れ子メンバーと分割ファイル間の参照は、取得済みグラフとReflectionからResoLoop側で解決済みです。この要望は、参照先の所有先・パスが不明な場合に、正確なIDから探索範囲を限定して情報を取得するためのものであり、シンボル名による参照管理そのものへの要望ではありません。所有先がすでに分かっており読み取り可能なら、通常のComponent／Slot読み取りから、ResoLoop側で不足するパスを取得できる可能性があります。未解決の1個のIDは、現在のツールの検索能力の限界を示すものであり、既存の読み取り操作の組み合わせでは一切解決できないという証拠ではありません。固定バージョンの[DataModelメッセージ一覧](https://github.com/Yellow-Dog-Man/ResoniteLink/tree/067afad3d1977b3806cbad077f4e8a534f56f451/ResoniteLink/Models/Messages/DataModel)も参照してください。

## 上流APIの不足と区別すべきResoLoop側の対応

- 文字列リテラル、大規模な観測結果の別ファイル保存、同名オブジェクトの保存、タグを付けない取り込み、baselineと編集意図の分離は、P0で対応済みです。
- 外部依存先の命名、構造化された入れ子メンバーセレクター、同一取り込み内の分割ファイル間参照、Slot属性の明示的な編集は、P1で実装済みです。直接参照、SyncObjectの一部、長さを変えない参照リストは、Componentを置き換えずに更新できます。独立したバンドルをまたぐ所有関係や、より広範なコンテナーへの書き込みはResoLoop側の課題として残りますが、この対応範囲の制約を、上流APIで不可能だと実証されたものとして扱わないでください。Slotの `UpdateSlot` は省略されたフィールドをすでに維持します。観測時にnullだったTagもResoLoop側で処理済みです。この部分更新のために新しい上流APIは不要です。Slotの条件付き更新については、要望4の原子性の不足に含まれます。
- **SyncPlaybackは、部分更新の意味が定義された、上流で対応済みのデータモデルです。** P0が今回観測した8個のメンバーを読み取り専用にしているのは、ResoLoop側の対応範囲の制約です。再生状態を読み書きできないというIssueは作成しないでください。[公開されているSyncPlaybackモデル](https://github.com/Yellow-Dog-Man/ResoniteLink/blob/067afad3d1977b3806cbad077f4e8a534f56f451/ResoniteLink/Models/DataModel/SyncPlayback.cs)を参照してください。
- 取り込みではアセットへの参照を維持します。持ち運び可能なアセットバックアップやProtoGraphの逆コンパイルは、別のワークフローです。
- `slotMember` への参照を新たに設定する操作は、ResoLoopの参照先型の検証処理で引き続き拒否されます。公開Slotモデルは型付きフィールドとそのIDをすでに公開しており、既存のバインディングは保持しています。現在の実装だけでは上流の変更が必要だとは証明できないため、APIを要望する前に、アダプターと型の検証情報による対応をResoLoop側で調査すべきです。これは、要望6の「所有先不明の要素を正確なIDから検索する機能」とは別の課題です。
