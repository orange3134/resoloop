# Inputs, state and existing UIX changes

For one typed value feeding two or more targets without write-back, use a runtime-verified ValueMultiDriver<T> instead of one ValueCopy<T> per target. On the observed runtime, ValueMultiDriver<bool> exposes the synchronized Value field and the Drives list of FieldDrive<bool> references. It has no Source member. If the value is owned state, connect ButtonToggle.TargetValue directly to Value and initialize Value only when created; no separate ValueField or ValueCopy is needed. When an external source must keep owning the value, use one source adapter such as ValueCopy<T> into Value, then fan out through Drives. Retain ValueCopy for a single target or when WriteBack is required; do not turn bidirectional bindings into one-way drivers.

In the shared-button example, one logic Slot holds ValueMultiDriver<bool> and BooleanValueDriver<float>, BooleanValueDriver<colorX>, and BooleanValueDriver<string>. Drives targets each BooleanValueDriver.State, and each driver owns its respective light, emission, or text field. This replaced four logic Slots and seven Components with one Slot and four Components while preserving the OFF/ON outputs. Component-level keys stay distinct. Group by purpose rather than creating one Slot per Component; separate layout, transforms, activation, lifetime, and provider identity only where those boundaries are needed.

For an already-applied composition, observe the current state and all exact targets before consolidation. Preserve the state-bearing Slot when possible; Component moves may recreate the Component, so do not assume its ID survives. Preserve input values when replacing a ValueField with ValueMultiDriver. Review a fresh diff including obsolete Slots and copies before explicit --prune --yes, and confirm removed Slots contain no unrelated user content. Re-inspect retained input bindings, every Drives entry and each output target, verify both states and restoration, then require a zero-change diff. Do not change existing recipe keys globally to optimize one instance.

The working input example used Button and TextField on the same Slot, wired to child Text and TextEditor. Inspect focus and editor targets rather than assuming TextField attachment is enough. Verify clicking, focus, actual typing, multiline behavior and disabled state as relevant. Keep decorative Graphics from interfering with the intended interaction target.

A caret drawn in a design file is a static sample. Use the native TextEditor/TextField caret for editable input and remove the sample caret when it duplicates native behavior. In test14, attaching Button to an Image also populated ColorDrivers; its normal/highlight/press/disabled colors could replace an intended transparent tint. Inspect the actual nested driver targets and alpha for all states, and decide whether native button coloring or custom drivers own the Graphic. A one-time Image.Tint write is insufficient when a driver owns it.

Build and verify native control semantics before expanding visual variants: dropdown open/close and selection, radio exclusivity, boolean toggle with both knob endpoints, tab selection and associated content, slider range and handle, progress source. A slider-shaped object is not necessarily a boolean switch. Use reflected generic type identities exactly, including the assembly prefix returned by type search/specialize; do not guess shortened Slider or BooleanValueDriver names. Inspect depth/material settings if an outline or OutlinedArc covers Text; test a local role-specific material before editing a shared one.

Native state-driven visuals can avoid unnecessary Flux graphs. The tested press effect used Button.IsPressed -> ValueCopy<bool> -> BooleanValueDriver<T>; switches coupled background color and knob position, and tabs/pagination coupled selected values to highlights. Verify reflected fields and reference wiring before reproducing a connection. Observe both transitions and the output, not merely the source value. Direct field probes are separate from user interaction tests. ResoniteLink 0.13.1 does not expose UIX SyncDelegate updates; do not invent delegate payloads. This does not prevent native UIX controls from functioning.

For a shared brightness slider, the user-authored ComponentSample0 reference observed on Resonite 2026.9.18.82 used three functional Components on one Drivers Slot: `[FrooxEngine]FrooxEngine.LinearMapper1D` mapped Source 0..1 to light intensity 0..4 through Target; `[FrooxEngine]FrooxEngine.LinearColorMapper` mapped the same Source to an emissive-color Target; `[FrooxEngine]FrooxEngine.ValueTextFormatDriver<float>` connected Source to Text with Format `{0:P0}`. Runtime Reflection confirmed the source references and FieldDrive targets. These are candidates for matching tasks, not a fixed recipe or permission to modify that reference Slot. Verify the current runtime and intended ranges, Clamp, AllowReverseMapping, color profile/interpolation, and formatting culture. The observed sample used sRGB color endpoints and displayed `100%`; the Flux example used Linear color and `100 %`, so the read-only comparison did not establish exact equivalence. Use meaningful grouping and names to keep these connections readable; when a direct driver no longer fits, consider Flux rather than extending a chain of workarounds.

Keep desired configuration in fields. User-editable input, selection, progress and intentional initial runtime values belong in initialFields. Assign ownership of driven Rect offsets, tint, padding and scroll position so apply does not overwrite the runtime driver. Do not move every field to initialFields to suppress differences. Canvas.Size belongs there only if the user is meant to resize it independently of the manifest.

An existing component preserves initialFields on reapply; recreating it applies them again. Before a necessary recreation, observe and preserve the affected typed values, consumer references and control state, then restore and compare afterward. Reapply convergence alone does not prove a migration preserved input. Do not recreate every UIX component as a routine update strategy.

Stable keys should retain roles across revisions. Use migrateFrom only for a verified intentional rename. Put repeated driver roles into named Logic Slots where useful, and use immutable identity evidence when available. Do not manufacture identity by assigning hash-derived UpdateOrder: it also changes runtime scheduling. Adding identityFields to a manifest does not populate old checkpoint evidence. Avoid manual state-ID rewriting as a normal recovery method.

On the test14 runtime, a Slider's existing field drives prevented a replacement BooleanValueDriver from retaining its TargetField until the old owner was removed. A successful write response did not establish a retained reference. Apply now rechecks symbolic references after lifecycle changes, retries mismatches once after an explicitly requested prune, and fails with `APPLY_REFERENCE_NOT_RETAINED` if they still do not stick. Inspect the target's current owner and the prune plan; the failure does not authorize implicit removal. New keys denote new roles: replacing a Slot key while retaining its display name now creates a distinct Slot, so pruning the old role cannot delete the new one. Use migrateFrom when retaining the object is intended.

In test13, moving existing UI under newly created UIX parents produced invisible content despite apparently correct fields. A dedicated live experiment on Resonite 2026.9.9.1136 / ResoniteLink 0.13.1.0 reproduced an invisible Image when the move preceded the parent's RectTransform and VerticalLayout. Preparing those components before moving kept the Image visible. The apply pipeline now prepares components and their field references before relocating existing Slots; its live fixture retained the child ID, rendered correctly, and converged without writes. This supports the ordering requirement in that case, not an internal engine cause or every Text/Mask migration. For a primitive reparent, explicitly prepare the parent first. Compare a tiny new control with the migrated one and inspect missing components/references and actual size. Do not broaden a failed repair to unrelated content or repeatedly prune/recreate without a bounded hypothesis.

For temporary combinations of width, content, or state, use `probe.kind: "set-members"` with a `values` object mapping stable member selectors to temporary values. It requires `safe: true`, `restore: true`, and `test --probe --yes`. All targets are preflighted before writes; attempted fields are restored in reverse order and read back even on failure or cancellation. `PROBE_RESTORE_FAILED` names unrestored targets. This is sequential compensation, not an atomic world transaction. Field assertions do not inspect pixels or prove real input; capture representative states separately and restore temporary edits in finally.

When verifying changes, preserve temporary input/selection values and restore them in finally, then read them back. Distinguish schema, reference wiring, field response, real input, visuals, convergence and portability. For shared state, include a two-user check or explicitly report single-user-only evidence. Saving/reloading the actual standalone part is a separate test from allowing an external shader role in item audit.
