# Resonite Build

Use rloop with --json as the primitive interface and keep source artifacts in the repository.

1. For a new repository without `.rloop.json`, run `rloop init` only in the user-approved project directory. This installs bundled project skills and their hash lock under `.agents/skills/`. Before accepting a bundled update, run `rloop skills sync --check`; use `--update` only after reviewing the report. Stop on `SKILL_SYNC_CONFLICT` because the installed skill has user edits or lacks a trusted prior hash.
2. Run `rloop doctor --json`, then `rloop status --json`. If connection fails, report the actionable error; do not invent a port. Optional Flux or log warnings do not block Slot/Component work.
3. Observe with a bounded hierarchy, then find and inspect the relevant target. Prefer stable IDs returned by the current session.
4. Before adding a Component or setting an unfamiliar member, run type search and type describe. Never guess Resonite type or member names. Use JSON arrays/objects as the canonical form for vectors, quaternions, colors, and nested values; comma strings are compatibility input only. When a described member is a list, pass supported field/reference elements as a JSON array and re-inspect the resulting element targets.
5. Make only changes authorized by the request. For experiments, create an unmistakable RLoop_Test Slot and keep all edits below it.
6. Use Slot/Component primitives or a checked-in schema v1 JSON apply document with `ownership.key` and a stable root `slot.key`. Prefer `$slot:key`, `$component:key`, `$member:key.MemberName`, and `$asset:key`; forward references are allowed. Pass `--state` when using those stable selectors with inspect or primitive commands after apply. Use include/parameters/prototypes/repeat to keep repeated content maintainable. Give every same-type Component on one Slot an explicit unique key; when insertion or reordering is plausible, add immutable managed `identityFields`. Managed references are also topology evidence after reconnect. Put desired configuration in `fields`, but put runtime-owned defaults in `initialFields` so reapply does not erase them. Stable Slot parent changes preserve the Slot ID; set `relocationTransform` explicitly to `world` when the world pose must survive the parent change, otherwise accept the default `local`. Component moves recreate at the destination and remove the exact managed source. Use `migrateFrom` only with a verified old stable key when intentionally renaming a Slot or Component key.
7. Before mutation, run `rloop validate FILE --json`, `rloop validate FILE --strict --json`, and `rloop diff FILE --changes-only --json`. Treat create/update/rename/delete reasons as the review boundary. If an existing root has no state binding, inspect the exact target and use `--adopt` only when the user intended rloop to manage it. Never use adoption to bypass ambiguity or ownership uncertainty.
8. Run apply and observe stderr progress; use `--profile` when performance matters and `--ndjson-progress` for machine-readable progress. Preserve the reported state file after cancellation or timeout and re-run the same apply to resume. Normal apply does not delete stale content. Before `--prune --yes`, run `rloop diff FILE --deletes-only --json` and confirm every candidate is intended and inside the ownership root. A stale parent Slot represents one recursive Slot deletion covering its managed descendants, so review that parent boundary rather than expecting separate child operations.
9. Re-inspect the changed Slot and Component. When cameras/tests are declared, generate `scene summary` and `capture` artifacts, then run `rloop test`. Treat `screenshotAvailable: false` as a wireframe-only visual check. InteractiveCamera looks along local Z+; inspect that axis and nearby occluders. Verify left/right GripPose separately. For UIX, keep competing Graphic components such as Image and Text on separate Slots; for a world-space backplate, inspect the actual UI Unlit material and depth settings instead of assuming ordinary image ordering. Avoid redundant double-sided or coplanar renderers. Execute a method probe only when its SyncMethod was verified through Reflection, the manifest marks it safe, and the user authorized `--probe --yes`; otherwise report structural-only verification. For a bounded field-state check, prefer a `kind: set-member` probe with a stable component/member target, `restore: true`, and `safe: true`; verify the report says the original value was restored.
10. If the result will be saved or distributed as a Grabbable, keep every required Component, runtime target, and Flux module below that Grabbable root, then run `rloop item audit ROOT --strict --json`. Treat an external Flux/world reference as a broken portable closure unless it is a deliberate runtime context dependency. Remember that changing a runtime clone/template does not update already spawned instances; preserve instance data and plan an explicit migration rather than reapplying initial values.
11. If ProtoFlux is needed, require the tested Flux-SDK series and managed-data check, edit `.pg` source, and run flux check. Prefer a module manifest for multiple modules or watch: it topologically builds and deploys only successful changes to a verified parent, can resolve `$slot:key` through world state, and can bind module inputs/outputs to stable slot/component/member keys. Re-inspect generated references after deployment and retain deploy state for non-atomic recovery.
12. On failure, use the JSON error code, context, suggested next action, Reflection, and logs when configured. Change one hypothesis at a time and stop if repeated attempts would broaden scope or risk unrelated content.

The status `connectionId` is scoped to one ResoniteLink connection, not a stable world identity. Refresh raw IDs after reconnect/restart and rely on managed key/path re-resolution.

ResoniteLink 0.13.1 does not expose UIX SyncDelegate members for update and does not expose Dynamic Impulse or CallInput trigger entrypoints as callable SyncMethods. Do not invent raw member payloads or report button/impulse behavior as runtime-verified; keep the result structural-only unless runtime Reflection exposes a supported method.
