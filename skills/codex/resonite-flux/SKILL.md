# Resonite Flux

Keep ProtoFlux logic in .pg files. Confirm `resoloop flux status --json`, the active ResoniteLink URL, and that `resoloop doctor --json` reports a successful managed-data check/build probe through either the configured path or Flux-SDK auto-discovery.

Run flux check for fast semantic diagnostics, then flux build. On failure, fix primaryDiagnostics first; diagnostics identify whether their raw text came from stdout or stderr and separate parse/type/cascade categories. Resolve the destination with find/inspect, and deploy using a verified parent ID or path. Deployment replaces only a same-named module child under that parent; unrelated children must remain untouched. Manifest deploy also runs exact-version runtime compatibility checks before mutation. `FLUX_RUNTIME_NODE_INCOMPATIBLE` means the source built on that pair but is known to fail when Resonite loads the record; use the reported bounded workaround. Do not generalize the quarantine to unobserved versions.

Discover exact node identities and ports with `resoloop flux node search` and `resoloop flux node describe`; do not infer a node from its short name. The catalog preserves duplicate short names by full runtime identity and is cached by Flux-SDK/library identity. A successful build that packs zero nodes is not deployable: keep a reachable entrypoint such as CallInput, LocalUpdate, a Dynamic Impulse receiver, or another graph consumer.

Design every graph with an explicit processing user and state scope. ProtoFlux impulses execute locally, but by default their mutations of the FrooxEngine data model—such as writes to non-driven synchronized fields, Slot or Component changes, and non-driven DynamicVariables—are synchronized to the session. Treat a data-model value as shared unless the exact type/member is verified as local or non-synchronized. Identify who owns every entry impulse: `LocalUpdate` fires once per user on that user's update, `LocalUser` is the user executing the current context, and user inputs on update/listener/event nodes must not be left ambiguous. Do not let per-user entrypoints write the same synchronized state unless multiple writers and their conflict behavior are intentional. For authoritative shared state, choose one writer, gate before the mutation, and make the authority policy explicit; the host is a common policy, not a universal default, and a headless session may be the host. Keep per-user input, presentation, prediction, and other client-only behavior local.

Choose storage by both lifetime and visibility: `Local` lasts only for one impulse context; `Store` persists across contexts but has a separate non-networked value for each user; `Data Model Store` and ordinary non-driven synchronized data-model fields are shared and synchronize when written; `Drive` continuously evaluates a target locally and is not a synonym for network synchronization. The manifest binding `mode: drive` only connects a module output to a member and does not change these multiplayer rules. Avoid synchronizing transient every-update values when a local calculation, per-user `Store`, event/intent sent once to an authoritative writer, or lower-frequency state transition is sufficient. For Dynamic Impulses, make the target hierarchy, receiver tag, originating/processing user, and intended local-versus-shared effects explicit. Verify multiplayer-sensitive graphs with at least two users or clearly report that only single-user structural behavior was checked.

For multiple modules or hot reload, keep a checked-in schema-v1 Flux module manifest with explicit `dependsOn`. Run `resoloop flux validate-manifest MANIFEST.json --json` before connecting or deploying. Prefer a `$slot:key` parent plus the matching world apply state; resoloop verifies a same-connection ID or resolves the saved path after reconnect. Declare every module `in`/`out` in `bindings`: use `mode: source` for an `in` name targeting `$slot:key`, `$component:key`, or `$member:key.Member`, and `mode: drive` for an `out` name targeting `$member:key.Member`. Never paste session-scoped IDs into a manifest. A command-line `--state` path is relative to the current directory; `worldState`, `source`, and `deployState` inside the manifest are relative to the manifest. Treat unbound ports, direction/type mismatch, and unresolved bindings as pre-deploy failures. Run `flux deploy-manifest` once, then use `flux watch MANIFEST.json` in the foreground. It topologically builds changed modules and deploys only successful builds. Preserve its deploy-state checkpoint and follow the non-atomic recovery report after failure.

For a bounded pool of interchangeable bullets, targets, effects, or enemies, deploy one controller module for the pool rather than one full graph per instance. Keep template-local Flux limited to unavoidable drivers or local adapters. Store instance state in consistently typed, namespaced DynamicVariables such as `Projectile/Active`, `Projectile/Velocity`, and `Projectile/Chain`; have the controller traverse the pool, claim inactive entries, update them, and reset all state before reuse. Keep allocation bounded and define exhaustion behavior. This prevents ProtoFlux node count and deploy cost from scaling with the number of pooled instances.

After deployment, use `parentSlotId` as the deploy destination and `moduleSlotIdBefore` / `moduleSlotIdAfter` as the re-observed direct module child identities; re-inspect that child and each generated input/output reference target. Put the module below the Grabbable root when it must travel with an item, and confirm with `resoloop item audit ROOT --strict`. Stop watch on cancellation. Do not reimplement compilation or generate ProtoFlux nodes directly—use Flux-SDK. Treat an untested Flux-SDK series reported by doctor as a compatibility warning that must be resolved before live deployment. Flux-SDK 1.9.x interface globals such as `IButton global` are rejected before deploy; prefer a concrete Component `element` input and convert it inside the module with `asDrivenGlobal`, or use a Dynamic Impulse bridge for event-only coupling. ResoniteLink 0.13.1 cannot itself fire that bridge, so runtime verification still needs an in-world producer.
