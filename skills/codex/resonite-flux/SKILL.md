# Resonite Flux

## Choose the implementation and trigger

Before writing a graph, consider whether a purpose-built Component directly satisfies the behavior. Prefer a verified Component when its wiring is simple and readable; use Flux for behavior unavailable through Components or when Component workarounds obscure the logic. Native controls and drivers can also surround a small Flux module. Compare state/synchronization, target ownership, and edge behavior as well as Slot/Component counts, and briefly explain the choice. Drive remains appropriate for exclusively controlled derived fields in either implementation. Do not replace clear Flux with a tangled Component-only chain just to reduce node count. For native state and display wiring, follow resonite-build/resonite-uix's Slot grouping and ValueMultiDriver guidance.

Choose the entrypoint from the behavior: dataflow for derived values, an input event for a discrete action, and an update node only for work that actually needs repeated integration or sampling. Reconstruct persistent presentation from state; keep one-shot effects such as a press sound on the event path so loading a saved state or joining does not replay them. A continuous-looking effect alone is not evidence that a per-frame impulse is needed.

## State, authority and initialization

Separate calculation authority from interaction permissions. A single updating user does not imply that other users must be prevented from pressing stop/reset or changing controls. Unless the requested behavior needs exclusive interaction, keep shared items open to ordinary users and restrict only the authoritative update path. Use IsNull for null tests rather than equality against an otherwise empty Store.

Choose local presentation or shared results from the item's purpose before choosing an update node. For an operator-computed shared simulation, prefer a verified Update with UpdatingUser explicitly bound to the operator and SkipIfNull=true when no operator must mean no updates. Write authoritative results to non-driven synchronized state; viewers may Drive presentation from that state without re-integrating it. Specify operator acquisition/release, departure, late join, initialization, and simultaneous claims. Every-update result writes may be appropriate for this purpose; assess transmission cost and observer interpolation separately. Do not claim strict single-writer acquisition from a client-side null check, or multiplayer correctness from a host-only field probe. The paired inertial-marker studies illustrate this distinction.

Session-relative timestamps need explicit initialization: a saved data-model deadline outlives WorldTime/T's origin. Reset it on a verified startup/load event rather than relying on initialFields or treating save/reload as an optional refinement. OnStart is per local node instance; use OnlyHost=true when initializing shared state so late-joining guests do not reset it. It also runs on host-side graph creation/replacement, which must be an intentional reset boundary. Check the mutable input's actual write target and host-gate reference after deploy. Do not claim world-reload or multiplayer verification from a deployment-time reset alone.

Keep startup/load initialization in a separate small Flux module when its trigger and lifetime differ from ordinary interaction or update logic. This makes its authority and write targets independently readable; do not require a separate module for every write. Choose reset behavior by state lifetime: intentionally saved counters/settings need not reset merely because a deadline does. For delayed actions with repeated input, define whether input replaces or extends the deadline and ensure an obsolete delayed action cannot undo the latest intent.

## Success-dependent flow and dedicated nodes

Use `bind _uniqueName = (Target <- value).OnWritten;` as the default for dependent writes; use distinct binding names to avoid SDK shadowing warnings. Plain adjacent writes in an impulse can generate Sequence, which continues regardless of Write failure. When both success and failure need handling, `switch (Target <- value) | OnWritten |> ... | OnFail |> ...` keeps those paths explicit. Reserve Sequence for intentional ordering of meaningful synchronous operations that must run regardless of earlier outcomes, such as attempting a conditional write and then recording the attempt even when skipped or failed. Do not use it as a substitute for asynchronous completion. Neither form provides rollback. Verify generated connections, not just source order; a bounded failure probe can distinguish the semantics.

For an in-place +1 operation, prefer a verified ValueIncrement over reading the value, adding 1, and writing it back when the behavior is equivalent. Preserve its OnWritten/OnFail continuations and match the variable's context as well as its value type. For a mutable data-model input on SDK 1.9.0, `ValueIncrement<FrooxEngine.ProtoFlux.FrooxEngineContext,int>(Variable=Attempts)` supports the same explicit `.OnWritten` binding; do not substitute the ExecutionContext-only specialization. Apply dedicated nodes where they clarify intent, not as a blanket rewrite of arbitrary arithmetic or a claim of cross-user atomicity.

For writes to mutable module inputs, prefer the assignment expression so the SDK selects the correct context-specific Write. The one-parameter `ValueWrite<T>(Variable=Input, ...)` compiled but failed runtime linking with SDK 1.9.0 and Resonite 2026.9.18.82; an assignment expression used with bind/switch selected the matching FrooxEngineContext variant. Treat this as version-specific evidence, not a ban on direct node calls with a verified context.

## Compile and deploy

Keep ProtoFlux logic in .pg files. Confirm `resoloop flux status --json`, the active ResoniteLink URL, and that `resoloop doctor --json` reports a successful managed-data check/build probe through either the configured path or Flux-SDK auto-discovery.

Run flux check for fast semantic diagnostics, then flux build. On failure, fix primaryDiagnostics first; diagnostics identify whether their raw text came from stdout or stderr and separate parse/type/cascade categories. Resolve the destination with find/inspect, and deploy using a verified parent ID or path. Deployment replaces only a same-named module child under that parent; unrelated children must remain untouched. Manifest deploy also runs exact-version runtime compatibility checks before mutation. `FLUX_RUNTIME_NODE_INCOMPATIBLE` means the source built on that pair but is known to fail when Resonite loads the record; use the reported bounded workaround. Do not generalize the quarantine to unobserved versions.

Discover exact node identities and ports with `resoloop flux node search` and `resoloop flux node describe`; do not infer a node from its short name. The catalog preserves duplicate short names by full runtime identity and is cached by Flux-SDK/library identity. A successful build that packs zero nodes is not deployable: retain a consumer appropriate to the behavior, such as an output Drive for derived values or an actual event/impulse entrypoint. Do not add LocalUpdate merely to keep a dataflow graph reachable; use it when ongoing update behavior is required and its processing user and lifetime are explicit.

Design every graph with an explicit processing user and state scope. ProtoFlux impulses execute locally, but by default their mutations of the FrooxEngine data model—such as writes to non-driven synchronized fields, Slot or Component changes, and non-driven DynamicVariables—are synchronized to the session. Treat a data-model value as shared unless the exact type/member is verified as local or non-synchronized. Identify who owns every entry impulse: `LocalUpdate` fires once per user on that user's update, `LocalUser` is the user executing the current context, and user inputs on update/listener/event nodes must not be left ambiguous. Do not let per-user entrypoints write the same synchronized state unless multiple writers and their conflict behavior are intentional. For authoritative shared state, choose one writer, gate before the mutation, and make the authority policy explicit; the host is a common policy, not a universal default, and a headless session may be the host. Keep per-user input, presentation, prediction, and other client-only behavior local.

Choose storage by both lifetime and visibility: `Local` lasts only for one impulse context; `Store` persists across contexts but has a separate non-networked value for each user; `Data Model Store` and ordinary non-driven synchronized data-model fields are shared and synchronize when written; `Drive` continuously evaluates a target locally and is not a synonym for network synchronization. The manifest binding `mode: drive` only connects a module output to a member and does not change these multiplayer rules. Avoid synchronizing transient every-update values when a local calculation, per-user `Store`, event/intent sent once to an authoritative writer, or lower-frequency state transition is sufficient. For Dynamic Impulses, make the target hierarchy, receiver tag, originating/processing user, and intended local-versus-shared effects explicit. Verify multiplayer-sensitive graphs with at least two users or clearly report that only single-user structural behavior was checked.

For multiple modules or hot reload, keep a checked-in schema-v1 Flux module manifest with explicit `dependsOn`. Run `resoloop flux validate-manifest MANIFEST.json --json` before connecting or deploying. Prefer a `$slot:key` parent plus the matching world apply state; resoloop verifies a same-connection ID or resolves the saved path after reconnect. Declare every module `in`/`out` in `bindings`: use `mode: source` for an `in` name targeting `$slot:key`, `$component:key`, or `$member:key.Member`, and `mode: drive` for an `out` name targeting `$member:key.Member`. Never paste session-scoped IDs into a manifest. A command-line `--state` path is relative to the current directory; `worldState`, `source`, and `deployState` inside the manifest are relative to the manifest. Treat unbound ports, direction/type mismatch, and unresolved bindings as pre-deploy failures. Run `flux deploy-manifest` once, then use `flux watch MANIFEST.json` in the foreground. It topologically builds changed modules and deploys only successful builds. Preserve its deploy-state checkpoint and follow the non-atomic recovery report after failure.

For a bounded pool of interchangeable bullets, targets, effects, or enemies, deploy one controller module for the pool rather than one full graph per instance. Keep template-local Flux limited to unavoidable drivers or local adapters. Store instance state in consistently typed, namespaced DynamicVariables such as `Projectile/Active`, `Projectile/Velocity`, and `Projectile/Chain`; have the controller traverse the pool, claim inactive entries, update them, and reset all state before reuse. Keep allocation bounded and define exhaustion behavior. This prevents ProtoFlux node count and deploy cost from scaling with the number of pooled instances.

Before replacing an existing graph, observe the exact module child, its transform, user-arranged nodes, and bound runtime state. Preserve the module's placement and state across replacement unless the change intentionally resets them; regenerated node layout is not preservation of a manually arranged graph. Save bounded structural evidence when needed for review. Distinguish build success, observed wiring, isolated impulse probes, actual interaction, multiplayer checks, and save/reload checks. Record user-reported acceptance without inferring unreported edge-case coverage.

After deployment, use `parentSlotId` as the deploy destination and `moduleSlotIdBefore` / `moduleSlotIdAfter` as the re-observed direct module child identities; re-inspect that child and each generated input/output reference target. Put the module below the Grabbable root when it must travel with an item, and confirm with `resoloop item audit ROOT --strict`. Stop watch on cancellation. Do not reimplement compilation or generate ProtoFlux nodes directly—use Flux-SDK. Treat an untested Flux-SDK series reported by doctor as a compatibility warning that must be resolved before live deployment. Flux-SDK 1.9.x interface globals such as `IButton global` are rejected before deploy; prefer a concrete Component `element` input and convert it inside the module with `asDrivenGlobal`, or use a Dynamic Impulse bridge for event-only coupling. ResoniteLink 0.13.1 cannot itself fire that bridge, so runtime verification still needs an in-world producer.
